# 04 客户端 / 服务端架构

## 一句话分工

**服务端是唯一的业务状态与执行权威**；客户端只做三件事：编辑卡、查看证据、渲染服务端算好的面板。
客户端不推导 DAG、不算任务状态、不缓存权威数据。

```
            ┌───────────────── 服务端（Node + PostgreSQL）─────────────────┐
            │  API v1 (contracts/api.v1.yaml)                        │
            │  ├ 仓储 model (contracts/db.v1.sql)                    │
            │  ├ 配置快照（来源仍是 Git 里的 project.yaml）            │
            │  ├ pipeline: validate / execute / gates                │
            │  └ 证据库（sha256 + 文件）                             │
            └───────────────▲──────────────────────┬────────────────┘
                            │ HTTP + Bearer        │ 下发的 agent schema/policy
        ┌───────────────────┴──────────────────────▼───────────────────┐
        │ 客户端                                                       │
        │  views/  纯渲染（只认 adapter + api，不碰 window/fetch）        │
        │  shell/  适配器（browser / tauri），只暴露 fs / term / agent   │
        │  web/    壳实现 A：单页 Web（无本地能力）                       │
        └──────────────────────────────────────────────────────────────┘
```

## 关键决策

### 1. 桌面壳选 Tauri v2

| 维度 | Tauri | Electron |
| --- | --- | --- |
| 能力白名单 | 原生 capability 模型，与"只暴露三类能力"同构 | 需自己写 IPC 校验 |
| 体积/内存 | ~10MB / 低 | ~150MB / 高 |
| 终端 PTY | 需要 Rust（portable-pty） | node-pty 现成 |
| 团队成本 | 需要 Rust | 纯 Node |

取舍：**capability 模型带来的安全边界价值 > PTY 的开发成本**。切换判据写死在 `contracts/ipc.v1.md`：
三周内交付不了稳定 PTY + 文件监听就换 Electron，只新增 `client/shell/electron.mjs`，视图与契约不动。

### 2. 三层：壳 / 视图 / 本地适配器

- `client/views/*`：纯函数式渲染，输入是服务端数据，输出 HTML 字符串；不 import 任何宿主 API。
- `client/shell/*`：唯一能触碰宿主的地方；`adapter.mjs` 定义契约与能力协商，`browser.mjs` 全降级，`tauri.mjs` 走 IPC。
- `client/web/*`：壳的 Web 实现 + 引导 + 事件委托。

这条约束让"Web 单页先跑、桌面壳后套"成立：壳换了，视图不用改一行。

### 3. IPC 只有三类能力

`fs`（文件）/ `term`（终端）/ `agent`（本地 agent）。没有第四类，也不允许视图直接调 `fetch` 之外的浏览器 API。
能力缺失时适配器返回 `E_UNSUPPORTED`，视图降级（隐藏入口），而不是报错。

### 4. 配置双写边界

| 数据 | 写方 |
| --- | --- |
| 项目/门禁/预设/agent 策略 | 服务端（源头是 Git 里的 `project.yaml`，服务端只做快照） |
| 需求卡 / 任务卡 | 客户端（`ETag` + `If-Match` 乐观锁） |
| 运行/证据 | 仅服务端 |

为什么配置不放进 DB 让客户端写：配置需要 code review、需要跟仓库版本一致、需要回滚。
放在 Git 里天然满足这三条，也彻底消除了"客户端与服务端各写一份"的冲突源。
在线注册项目（写 API）留到 v1.1，且只写 DB 快照，不回写 Git。

### 5. agent 接入

- 服务端下发 `agent/v1` schema 与执行策略（`GET /agent-config`），客户端**只读**。
- 客户端可配置**本地** agent（命令、模型、VSCode Claude Code 的调用方式），只存在本地。
- 触发执行时以 `localOverride` 上报，服务端按 policy 判定：v1 明确拒绝把实现者覆盖成远端模型（防止代码出网）。
- VSCode Claude Code 两种接法：`headless-cli`（跑 `claude -p`，能拿 JSON 输出，可自动化）与
  `interactive-uri`（只唤起人工会话，拿不到结构化输出）。默认前者。

## v1 范围

已实现：项目/配置快照、需求与任务卡读写（乐观锁）、DAG 与面板聚合、执行（worktree 隔离 + 三段门禁 + 证据）、
证据清单与原文（sha256 校验）、事件流、agent 配置下发、Web 面板（流程视图 / 卡视图 / 证据视图）。

未实现（v1.1 起）：在线注册项目、并发队列与配额、自动合并、卡改动导出回仓库 YAML、
桌面壳的 Rust 侧（PTY/文件监听/agent sidecar）、多租户与角色权限。

## 演进顺序

1. v1（当前）：契约 + 存储 + API + Web 面板 + 服务端执行闭环。
2. v1.1：执行队列（异步 run + 轮询/SSE）、项目在线注册、卡导出回 Git。
3. v1.2：Tauri 壳（PTY + 文件监听 + 本地 agent sidecar），视图零改动。
4. v2：多租户、配额、审计导出；若 API 需破坏性变更则开 v2 并行。
