# 06 容器化开发与联调

目标：**后端跑在容器里，前端跑在宿主机**。后端容器化换来"环境一致 + 部署形态可验证"，
前端不进容器是为了保住 Vite 的 HMR 速度（容器里改一行等两秒，会毁掉联调体验）。

## 拓扑

```
        宿主机                            Docker
┌──────────────────────────┐    ┌───────────────────────────┐
│ pnpm dev (Vite :5173)    │───▶│ api 容器 :8787            │
│   /api  ──proxy──────────┼───▶│   server/index.mjs        │
│                          │    │   node --watch            │
│ pnpm build → dist/       │    │   bind mount: ./ → /app   │
└──────────────────────────┘    └───────────────────────────┘
                                        │
                                   data/ repos/ worktrees/
                                   archive/（都在宿主机上，可直接看）
```

## 开发用法

```bash
# 1. 后端进容器（代码改了自动重启，因为 --watch + bind mount）
docker compose up api

# 2. 前端在宿主机（另开一个终端）
cd client && pnpm dev     # http://127.0.0.1:5173 ，/api 代理到容器 :8787

# 3. 想让容器自己托管页面（不走 Vite）
cd client && pnpm build   # 产物进 client/apps/web/dist，容器直接托管 :8787
```

常用：

```bash
docker compose logs -f api          # 看后端日志
docker compose exec api sh          # 进容器排查
docker compose exec api node server/test/api.test.mjs   # 在容器里跑契约测试
docker compose down                 # 停掉
```

## 为什么用 bind mount 而不是把代码打进镜像

- `data/`、`repos/`、`worktrees/`、`archive/` 都在宿主机上，联调时能直接翻证据、看 worktree 里的 diff；
- 改后端代码不用重建镜像（`--watch` 会重启进程）；
- 代价：Windows 上挂 `E:` 盘进容器会慢一些（文件事件与 I/O 都有损耗），如果卡，把仓库挪到 WSL 文件系统（`\\wsl$\...`）再挂。

## 部署形态（生产镜像）

```bash
docker build -f docker/Dockerfile -t devloop-core:latest .
docker run --rm -p 8787:8787 \
  -e DEVLOOP_TOKEN=change-me \
  -v devloop-data:/app/data \
  devloop-core:latest
```

两段构建：`web` 阶段用 pnpm 装依赖并 `pnpm build`，`runtime` 阶段只带 Node + git + 服务端源码 + 前端产物。
运行时镜像里**没有 node_modules**（服务端零依赖），镜像保持小。

或本地验证部署形态：

```bash
docker compose --profile prod up --build    # http://127.0.0.1:8788
```

## 三个必须知道的点

1. **默认只发布到回环**（`127.0.0.1:8787`）。接口只靠 token 保护，别默认暴露到局域网；
   要远程联调时显式改端口映射，并把 `DEVLOOP_TOKEN` 换掉。
2. **`DEVLOOP_HOST`**：容器内必须 `0.0.0.0` 才能从宿主机访问；宿主机直跑时默认 `127.0.0.1`。
3. **git 必须在镜像里**：`bootstrap`（生成示例仓）和任务执行（worktree）都依赖它，两个镜像都装了。

## 镜像里验证过什么

- `docker compose exec api node server/test/api.test.mjs` — 契约测试在容器内同样通过（Node 24 + git，无隐式依赖）。
- 冷启动：`data/` 为空、`repos/` 为空时，entrypoint 会先 `bootstrap` 再启动，服务可用。

## 排查：端口被占

`docker compose up` 起不来、容器日志为空，先查 8787 是不是被宿主机上残留的实例占着：

```bash
# Windows
netstat -ano | findstr :8787
# 或直接看容器状态
docker compose ps -a
```

自己在宿主机跑过 `node server/index.mjs` 又忘了停，是最常见的冲突来源。
