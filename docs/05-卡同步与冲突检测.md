# 05 卡同步与冲突检测

## 问题

卡有两个副本：**DB**（客户端编辑的权威）和**仓库 YAML**（代码评审与版本管理的权威）。
两个副本一定会分叉：有人在 UI 里改了卡，有人在 PR 里改了 YAML。没有同步机制时只有两种结局——
要么启动时被文件覆盖，要么导出时把别人的 PR 改动冲掉。

## 状态机

每张卡有三份哈希参与比较：

| 哈希 | 含义 |
| --- | --- |
| `dbSha` | DB 中该卡规范化 JSON 的哈希 |
| `fileSha` | 仓库 YAML 文件字节的哈希 |
| `baseDbSha` / `baseFileSha` | **上次同步时**记录的基线 |

| 状态 | 条件 | 建议动作 |
| --- | --- | --- |
| `synced` | dbSha = baseDb，fileSha = baseFile | 无 |
| `db_ahead` | 只有 DB 变了 | 导出 |
| `file_ahead` | 只有文件变了 | 导入 |
| `conflict` | 两侧都变了 | 人工 |
| `db_only` | DB 有、文件没有 | 导出（新建） |
| `file_only` | 文件有、DB 没有 | 导入（新建） |
| `untracked` | 没有基线，两侧都有 | 人工（provenance 不明） |

关键点：**基线不是"当前内容"，而是"上次握手时双方的样子"**。所以判断"谁改了"永远不需要猜测。

## 动作

```bash
# 看状态
GET  /api/v1/projects/{p}/card-sync

# 预览导出（不落盘）
POST /api/v1/projects/{p}/card-sync/export   {"dryRun": true}

# 正式导出（只处理 db_ahead / db_only）
POST /api/v1/projects/{p}/card-sync/export   {}

# 从仓库导入（只处理 file_ahead / file_only）
POST /api/v1/projects/{p}/card-sync/import   {}
```

导出的写入是原子的（临时文件 + rename），且**写前自检**：渲染出的 YAML 必须能被解析回同一张卡，
否则整卡跳过并报 `failed:render-roundtrip`，绝不把仓库写坏。

## 冲突解决

默认 `safe`：导出与导入都不会碰 `conflict` 卡，两侧内容保持原样，等人工判断。

需要明确的强制动作时才用 `prefer: "force"`：

| 动作 | 语义 | 结果 |
| --- | --- | --- |
| `export` + `force` | **以 DB 为准** | 覆盖文件 |
| `import` + `force` | **以文件为准** | 覆盖 DB |

强制动作会写 `card.exported` / `card.imported` 事件，payload 里带 `forced: true` 与 `previousState`，
审计时能查到"是谁在什么状态下强推的"。

Web 面板只提供 safe 路径（预览 / 导出 / 导入），强制解析刻意留在 API 与 CLI ——
覆盖仓库文件应当是 deliberate 的，不该是一次误点。

## 与 Git 流程的配合

导出写的是**工作区文件**，不会 commit。标准流程：

```
UI 改卡 → 导出 → git diff 评审 → commit / PR → 合并
```

导入则相反：别人在 PR 里改了 YAML，合并后执行一次 `card-sync/import`（或重启服务，启动同步会自动导入无冲突的部分）。

## 启动同步（重要）

每次启动都会跑一次同步，但**只做安全方向**：

- 无基线 → 视为迁移，以文件为准建基线；
- `file_ahead` → 自动导入（DB 没动过，导入是安全的）；
- `db_ahead` → **跳过**，等人工导出（否则 UI 的改动会在重启时被文件覆盖）；
- `conflict` → 跳过并记录。

这条保证了"在 UI 里改的卡，不会因为服务重启而丢失"。

## 已知限制

1. **注释会丢失**：导出即按规范化格式重写文件。建议卡文件不写注释，或把说明放在 `summary` / `objective` 里。
2. **不感知 Git 分支**：同步比对的是工作区文件。切分支后执行导入前，先确认工作区是你想要的那个分支。
3. **单实例**：并发写同一个文件没有锁。多实例部署前需要加文件锁或把导出收敛到单一写者。
4. **不处理 `policy` 字段**：卡里的 `policy.deny_write` 已由平台配置承担，导出不写它。

## 为什么不做双向自动合并

自动合并 YAML 会引入"合并后语义不正确"的风险（例如 DAG 依赖被合并成环），而且事故现场极难复盘。
当前策略是**只在无歧义时自动化**（单边变更），双变更一律停下来要人决定——这类卡的数量在实践中很少。
