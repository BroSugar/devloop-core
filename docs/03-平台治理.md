# 03 平台治理：门禁、证据、权限与推广顺序

平台化的难点从来不是"多接几个仓库"，而是**一致性**：同样的判据、同样的证据、同样的责任边界。

## 统一门禁的含义

- **入口统一**：所有项目都通过 `build / lint / test` 三段进入验证，顺序固定、短路执行。
- **实现各异**：命令来自 preset，`pnpm build` 与 `go build ./...` 是同一个抽象位。
- **可混用**：任务卡的 `verify` 既可以引用门禁名（`build`），也可以写裸命令（`go test ./internal/money -run TestSum`）。
  引用名让平台能统一升级；裸命令让单卡能定向。两者都留，是因为只留一个都会出事。
- **禁止**：`|| true`、管道掩盖退出码、`--no-verify` 之类的跳过标记（可在 lint 阶段加规则扫描卡文件）。

## 证据链

每次执行产生一个证据包：

```
archive/<project>/<requirement>/<task>/attempt-<n>/
  result.json      判定结论、变更文件、越界明细、各阶段退出码与耗时
  changes.txt      变更文件清单
  diff.patch       完整 diff
  00-build.log     三段门禁的原始输出（含失败堆栈）
  01-lint.log
  02-test.log
  merge-verify/    合并到主仓后的复验日志
  manifest.json    schema/时间/结论 + 每个文件的 sha256
```

- `archive/index.jsonl` 是全局索引，跨项目可查询。
- `archive-verify` 重算全部哈希，检测篡改与丢失（合规/审计的最小实现）。
- 保留策略建议：通过的包保留 30 天，失败的包与涉及高危改动的包**永久保留**——复盘价值在失败样本上。

## 权限与隔离

| 边界 | 做法 |
| --- | --- |
| 写域 | 任务只能改 `scope.write`；`deny` 优先；diff 逐文件比对 |
| 判据 | 测试文件永久禁改（平台默认 + 需求卡策略双层） |
| 工作区 | 每个任务独立 `worktrees/<project>/<task>`，与主仓物理隔离 |
| 网络 | 模型调用默认关闭，需显式开关 |
| 密钥 | 只存环境变量名，配置文件里不出现明文 |
| 合并 | 串行合并 + 主仓复验，失败回滚 |

多租户上线前必须补的两点：
1. **并发调度**：现在是串行执行；多项目并行要做队列 + 每项目并发上限（gateway 侧限流）。
2. **配额**：按项目统计 token 与执行时长，超限降级到 `human-only`。

## 推广顺序（从单仓到平台）

1. **单仓单需求**（已完成）：证明"需求卡 → 全绿"可行。
2. **单仓多需求**：跑 10 条真实需求，盯一次通过率与越界率。
3. **双仓异构**（本仓库已做）：证明配置化接入成立（Node + Go 两栈，两种卡模式，两张 AI 路由）。
4. **团队接入**：每个团队自己写 `project.yaml` + preset，平台只审 preset 与策略。
5. **常态化**：需求进来自动出预发版本，人只做里程碑审批与高风险项。

判据：**阶段 3 不成立就不要往阶段 4 走**。判断标准是"新仓接入是否真的只改配置"——
如果每次接新仓都要人改内核，说明抽象层漏了，先补抽象。

## 指标（平台级）

| 指标 | 定义 | 用途 |
| --- | --- | --- |
| 接入成本 | 新仓从注册到首次跑绿的人时 | 平台抽象是否有效的唯一硬指标 |
| 一次通过率 | 首次执行 PASS 的任务数 ÷ 总任务数 | 判据与上下文质量 |
| 越界率 | 出现写域越界的执行数 ÷ 总执行数 | 卡粒度健康度 |
| 失败归因分布 | 引擎缺陷 / 仓库配置 / 实现缺陷 / 判据缺陷 | 决定下一步该修谁 |
| 升级率 | 重试耗尽转人工的比例 | 直接等于人的负担 |

本次实测的归因分布：**引擎缺陷 1、仓库配置 2、实现缺陷 0**。
这个分布说明平台化早期投入应该在"工作区与 git 语义"，而不是在模型上——
任何让你觉得"模型不行"的现象，先查这两类。
