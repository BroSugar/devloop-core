本文件记录**不属于当前功能分支**的事项：待排期需求、已知问题与阻塞判定、流程约定。

## 待排期需求

### PRD 审核环节（记录于 2026-11-24）

**背景**：产品产出 PRD 相关文档，上传云平台前缺少把关。

**要求**：
1. 先由专业产品 agent 对文档做完善（补齐结构、口径、边界、异常路径）；
2. 再按"标准文档"规范做审核；
3. 审核通过后才允许上传云平台。

**约束**：**不插队**。等前端这一轮（shadcn/ui + pnpm workspace + 容器化）落完并合并后，
再按 brainstorming 流程走设计（设计文档 → 计划 → 实施），不在当前分支上动。

**设计前需要明确的点**（留给 brainstorming）：
- "标准文档"的判定口径：检查清单、打分阈值，还是人审签字？
- 审核主体：产品 agent 自审、独立审核 agent、人审，还是双签？
- 与现有卡体系的衔接：PRD 是否先落成需求卡（`REQ-*`）再上传，还是独立通道？
- 云平台上传的接口形态与幂等性、失败回退、版本留痕；
- 证据链：审核记录是否进 `evidence`，是否需要可追溯。

## 流程约定：缺陷回归

此后**测试、联调、评审发现的问题统一走缺陷回归**，不再"看到就顺手改"：

1. 先写一个能稳定复现失败的测试（红），并在本地确认它确实因为该缺陷而失败；
2. 最小改动修复，测试转绿；
3. 跑全量回归（`npm run verify` + 前端构建）确认没有连带破坏；
4. 记录：缺陷一句话 + 复现测试名 + 修复提交。

阻塞级缺陷当轮修完才允许合并；非阻塞缺陷登记进本文件的"已知问题"表，排期处理。
没有复现测试的"修复"不算修完——这与项目里"判据先行"的原则一致。
