# 01 拆解逻辑：单仓前后端的可判定流水线

## 一条不变量

> 每一层的输出必须是**可版本化文件**，且下一层能用**一条命令**判定它是否合格。

违反这条不变量，任何自动化都会退化成"看起来在跑"。

## 分层与判据

| 层 | 输出工件（本仓库里的位置） | 机器判据 | 人的角色 |
| --- | --- | --- | --- |
| L0 需求 | `pipeline/spec/REQ-*.yaml` | 每条 `acceptance` 必须有 `verify_by` 且文件存在 | 审"要不要做"、审矛盾项 |
| L1 契约 | `packages/contracts/src/*.mjs` | 契约测试（枚举、错误码、校验） | 审字段与错误码是否够用 |
| L2 任务分解 | `pipeline/tasks/T-*.yaml` + `_graph.json` | `plan.mjs`：无环、写域不重叠、写域落盘、验收标准被引用 | 审 DAG 形状与粒度 |
| L3 实现 | worktree 里的 diff | 写域越界检查（git diff ⊆ scope.write，且 ∉ deny） | 不参与 |
| L4 验证 | `.runs/<task>/attempt-n/0X-*.log` | build + lint + targeted test 全绿 | 抽查失败归因 |
| L5 评审 | 同上 + `diff.patch` | 人工按 autonomy 分级介入 | 高风险项人审 |
| L6 集成 | main 上的全量验证 | 需求级集成任务（全量测试） | 里程碑放行 |

本仓库里 L6 由 T-0124 承担：它自己的 verify 就是**全量测试**。所以"需求完成"的判据不是"四个任务都过了"，
而是"全量套件在 main 上全绿"——这两者不是一回事，中间那次全量红（见 README 实测）就是证据。

## 为什么按"契约 / 领域 / 接入"拆，而不是按"前端 / 后端"拆

按前后端拆的典型问题：两边对错误码、枚举、状态机的理解会漂移，漂移只能在联调时发现，而联调是人工的、
最慢的环节。本仓库的拆法把漂移点前置成一个**可测的契约包**：

- T-0121 先把 `CANCEL_REASONS`、`CANCEL_ERROR`、`isCancelableStatus`、`validateCancelRequest` 定死并测试；
- T-0122（后端领域）与 T-0123（前端状态机）**并行**实现，都只依赖契约；
- T-0124 只做接入与串联。

副产物：T-0122 和 T-0123 的写域完全不重叠，可以并发执行；合并走串行队列，互不冲突。

## 三条机械约束（缺一条，闭环就破）

1. **判据前置**：`verify_by` 指向的文件不存在 → `plan.mjs` 直接拒绝。没有测试的需求不许进流水线。
2. **写域落盘**：`scope.write` 必须能映射到真实路径。`plan.mjs` 检查"新建文件的父目录存在 / 通配符的静态前缀存在"，
   堵住 `scope.write: ["*"]` 这种看起来能跑、实际无约束的卡。
3. **diff 越界即失败**：执行期逐文件比对 git 变更，`deny` 优先于 `write`。这是**反作弊**的关键一条：
   测试文件是判据，实现任务永远不许改它。

## 任务粒度

经验值（对应本仓库的卡）：

- 一张卡 ≤ 3 个文件、≤ 200 行改动；超过就拆。
- 一张卡的 verify ≤ 3 条命令；超过说明它其实做了两件事。
- 一张卡的 acceptance 引用 1–5 条验收标准；引用全部说明粒度太粗。
- 卡与卡之间写域零交集；有交集就必须有 `depends_on` 串行化（`plan.mjs` 会检查）。

## 上下文边界（决定 agent 能不能落地）

任务卡的 `scope.read` 就是**给实现者的上下文边界**：in_scope 文件 + 被依赖的接口 + 相关测试，其余不给。
单仓大仓库如果不做这一步，上下文会失控；这条约束比"把模型换大"更有用。
