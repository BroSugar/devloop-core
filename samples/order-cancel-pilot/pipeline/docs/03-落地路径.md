# 03 落地路径：从单条需求到常态化流水线

原则：**先证明一条需求能闭环，再谈规模化**。本仓库就是"一条需求"的样板，下面是把样板复制到真实仓库的顺序。

## 阶段 0：可验证基线（1–2 周，生死线）

- 选定**一个中等复杂度模块**（本仓库对应 `apps/api/src/orders`）。
- 一条命令跑完全量验证，单次 < 10 分钟；超过就先优化测试，否则 agent 每次迭代都在等。
- 把"最近 3 个真实 bug"补成回归测试——这决定后面的判据质量上限。

准入：`npm run verify` 一条命令全绿。
不达标：**停止**，不要进入阶段 1。没有基线的自动化只会放大噪声。

## 阶段 1：任务级自动化（2–4 周）

- 人写任务卡，agent 在 worktree 里实现，人只审 PR。
- 每周跑 5–10 张真实卡，记录：一次通过率、越界率、平均返工次数、人工介入分钟数。
- 指标门槛：**一次通过率 ≥ 50%** 且 **越界率 < 10%**。
- 未达标：问题在判据或上下文，回阶段 0 补测试/补仓库地图，**不要**去调 prompt。

## 阶段 2：需求 → 任务 DAG（1–2 月）

- 用 `02-卡规范.md` 的分解 prompt 产出任务卡，人只审 DAG 与契约。
- 指标：DAG 人工返工率 < 30%；单需求端到端 lead time 可测。
- 未达标：通常是领域知识没沉淀（接口约定、历史包袱），补 ADR 与仓库地图。

## 阶段 3：验证与评审增强（1–2 月）

- 加契约测试、变异测试（关键模块杀伤率守基线）、自动 review。
- 人的评审从"逐行读 diff"转为"审结论与高风险项"。
- 指标：**漏出率**（上线后缺陷 ÷ 合并前通过的任务数）不得劣于人工流程；这是唯一有意义的评审指标。

## 阶段 4：需求级常开（持续）

- 需求进来自动出预发环境可运行版本；人只做里程碑放行与高风险审批。
- 指标：需求到预发 ≤ 1 天；自动修复重试 ≤ 2 次；升级率（转人工）持续下降。

## 指标定义（统一口径，否则无法比较）

| 指标 | 定义 | 用途 |
| --- | --- | --- |
| 一次通过率 | 首次 run 即 PASS 的任务数 ÷ 总任务数 | 判据与上下文质量的综合代理 |
| 越界率 | 出现写域越界的任务数 ÷ 总任务数 | 卡粒度与 scope 写法的健康度 |
| 升级率 | 自动重试耗尽后转人工的任务数 ÷ 总任务数 | 直接等于人的负担 |
| lead time | 需求卡 `ready` → 集成门禁绿 | 端到端吞吐 |
| 漏出率 | 上线缺陷数 ÷ 合并前通过任务数 | 唯一有意义的评审指标 |

## 生产化时必须补的两件事

1. **需求级集成分支**。本样板为演示简化：任务直接合入 main，main 上的测试在需求完成前是红的
   （验收测试先行）。生产上应改为 `feature/REQ-xxx` 集成分支，全部任务绿 + 全量绿之后整体合入 main，
   避免主干长期红。
2. **迁移、安全、支付类任务强制降级**。`autonomy: human-only`，无论测试多绿都必须人审 + 双人复核。

## 什么时候该放弃自动化这条需求

- 验收标准写不出来（连业务方都说不清成功是什么样）；
- 改动半径覆盖超过 3 个模块且接口未定；
- 需要从未被记录过的线上状态反推规则。

这三类交给人的成本，低于训练机器理解它们的成本。
