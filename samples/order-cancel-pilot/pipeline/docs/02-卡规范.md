# 02 卡规范：需求卡与任务卡

卡是流水线唯一的输入契约。字段少、规则硬，才能被机械校验。

## 需求卡 `pipeline/spec/REQ-*.yaml`

| 字段 | 必填 | 规则 |
| --- | --- | --- |
| `id` | 是 | `REQ-NNN` |
| `title` | 是 | 一句话 |
| `status` | 是 | `draft` / `ready` / `accepted`，只有 `ready` 才可进流水线 |
| `autonomy` | 是 | `auto` / `assisted` / `human-only`，需求级默认自治等级 |
| `summary` | 是 | 多行文本，写给实现者看的行为描述 |
| `policy.deny_write` | 否 | 全局禁改路径，建议至少含 `**/*.test.*` 与 `pipeline/**` |
| `acceptance[]` | 是 | 见下 |

`acceptance` 每一项：

```yaml
acceptance:
  - id: AC-2
    text: 取消后释放库存占用；重复取消幂等，库存不会被释放两次
    verify_by: apps/api/src/orders/cancel.test.mjs
```

硬规则：**`verify_by` 指向的测试文件必须已存在**。写不出验证方式的需求，要么回退去澄清，
要么把 `autonomy` 标成 `human-only` 并且不进自动化队列——不允许"假装验证过"。

## 任务卡 `pipeline/tasks/T-*.yaml`

| 字段 | 必填 | 规则 |
| --- | --- | --- |
| `id` | 是 | `T-NNNN` |
| `title` | 是 | 动宾结构，能当 commit message |
| `requirement` | 是 | 所属需求卡 id |
| `autonomy` | 是 | 本任务的自治等级 |
| `depends_on` | 否 | 任务 id 数组，DAG 边 |
| `objective` | 是 | 块文本，只描述**行为**，不描述实现细节 |
| `scope.write` | 是 | 非空数组，允许改动的路径 |
| `scope.read` | 否 | 提供者应在上下文里给到的文件（上下文边界） |
| `scope.deny` | 否 | 本任务额外的禁改路径 |
| `acceptance` | 是 | 引用需求卡里已存在的 AC id |
| `verify` | 是 | 非空命令数组，人能原样复制到终端跑 |

### scope 的三条硬规则

1. **落盘**：无通配符的路径必须是已存在文件，或父目录已存在（新建文件）；有通配符的必须静态前缀存在。
   `scope.write: ["*"]` 会被拒。
2. **不重叠**：两张卡写域相交且无 `depends_on` 关系 → `plan.mjs` 报错。这是并发安全的前提。
3. **diff 越界即失败**：执行期用 `git status` 逐文件比对，`deny` 优先于 `write`。
   测试文件永远在 `deny` 里——**实现者不能靠改测试让自己变绿**。

### verify 的写法

```yaml
verify:
  - node pipeline/tools/gates/smoke.mjs          # build
  - node pipeline/tools/gates/lint.mjs           # lint
  - node pipeline/tools/gates/tests.mjs apps/api/src/orders   # 只跑相关测试
```

- 顺序即执行顺序，**短路**：第一段失败就不再跑后面。
- 面向单任务的 verify 用**定向测试**；需求级集成任务才用全量测试。
- 命令里不要写 `|| true`、不要吞错、不要用管道接 grep（会掩盖退出码）。

## 反模式清单

| 反模式 | 后果 |
| --- | --- |
| `scope.write` 写成整个仓库 | 越界检查形同虚设 |
| 把测试文件放进 `write` | agent 会自动"修测试"而不是修实现 |
| `verify` 只写 `npm test`（全量） | 任务之间互相阻塞，并行度归零 |
| 一张卡改 10 个文件 | 失败归因困难，重试成本爆炸 |
| `objective` 写成"实现订单取消功能" | 实现者只能猜，返工率飙升 |
| 需求卡里没有 `verify_by` | 无法判定完成，等于把人工评审变成唯一判据 |

## 分解 prompt 约定（自然语言 → 任务卡）

分解是 LLM 的活，`plan.mjs` 只校验。喂给分解 agent 的输入与要求：

```
输入：需求卡原文 + 仓库地图（模块职责、目录树、现有接口）+ 已有验收测试清单
输出：N 份任务卡 YAML，必须满足
  1. 每张卡 scope.write 是具体文件或具体目录，不得是仓库根或跨模块通配
  2. 任意两张卡 scope.write 不相交；相交则必须给出 depends_on
  3. 每张卡 verify 必须是 3 条以内、可复制执行的命令，且定向到本卡涉及的模块
  4. 每张卡 acceptance 只引用需求卡里已存在的 AC id
  5. 第一层必须包含"契约/接口"任务，且它不被任何实现细节阻塞
  6. 最后必须有一张集成任务，verify 为全量测试，depends_on 其余全部任务
禁止：修改测试文件、拆分到 >10 张卡、把同一个文件分给两卡
```

产出后必须跑 `plan.mjs`；校验失败就把错误原文回喂给分解 agent，最多 3 轮，超出转人工。
**分解结果永远由人批准后再进入执行**——这是本方案里唯一不能省的人工闸门。
